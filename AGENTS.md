# AGENTS.md

## Mission

Maintain one cohesive, research-aware stack from requirements through release evidence.

These instructions govern the playbook source repository. Adoption follows `ADOPT.md`, `STACK.md`, and the target repository's own instructions.

## Start here

1. Read `README.md`, `STACK.md`, and `ADOPT.md`.
2. Inspect the current working tree before editing.
3. Keep the stack roles connected through requirement IDs and evidence links.
4. Run `python3 tools/verify_playbook.py` after changing prose, links, or sources.

## Compass and drift control

The README's purpose and the current authorised request are this repository's compass: help developers and coding agents deliver useful, correctly verified changes without replacing native tools with process machinery.

- Before selecting a batch, name the user outcome it advances or the demonstrated blocker it removes. Prefer applying an adequate existing rule over adding another document, tool or gate.
- Define the bounded acceptance evidence and stopping condition before editing. A passing suite, completed review or larger evidence packet is not itself a user outcome.
- After a handback, interruption or compaction, reconcile the current outcome, accepted evidence and next eligible action. Do not restart discovery or repeat unchanged green checks merely because the conversation changed.
- Repair concrete findings and rerun affected evidence. Stop review when the agreed claims are supported; change scope explicitly through the responsible owner instead of moving the finish line.
- Keep a blocked optional tool or criterion scoped to its actual dependency. Preserve real refusals, security and approval boundaries; the compass does not authorise bypassing them.

These are James's engineering choices informed by recurring field experience, not a controlled finding that this workflow is universally optimal. Preserve dated research and distinguish measured findings, extrapolation and adopted policy.

## Research rules

- Label standards, empirical studies, engineering reports, documented capabilities, and James's stack choices separately.
- State the limits of empirical findings.
- Treat official tool documentation as capability evidence.
- Avoid claiming universal superiority for a selected tool or workflow.
- Keep operating choices explicit instead of deleting the stack they organise.

## Stack rules

- Keep the complete chain visible in `STACK.md` and `ADOPT.md`.
- Keep sound project equivalents through clear substitution rules.
- Put tool-specific setup in the target repository, not this source playbook.
- Use synthetic examples and data.
- Keep credentials, local reports, and generated evidence out of this repository.

## Handoff

Report changed files, checks run, exact results, research boundaries, and unresolved source questions.
